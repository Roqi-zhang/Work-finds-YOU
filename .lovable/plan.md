# 时间轴状态同步、决策文案精简、前后端数据架构规划

## 1. 投递状态改变后，右侧时间轴同步

现在切换状态只改了时间轴条目的文字，节点仍是灰色空心点，且位置不动（仍按原始投递日期排序）。改为：

- 状态为「已投递 / 面试中」→ 节点点亮（实心黑，`.on`）；「待投递 / 结束」→ 保持灰色空心。
- 状态改变时记录「状态更新日期 = 今天」，该条目的时间戳改为这个日期，并把它重新插入到时间轴中正确的时间位置（按日期倒序，最新在上）。
- 更新结果写入本地存储，刷新后保留（键沿用 `wfy.entryStatus`，值扩展为 `{status, updatedAt}`）。
- 同时按新状态重算右下角统计（Active / Interview / Offers）。

## 2. 匹配页「一句话决策」正文去掉

删除 01 模块标题下方那段结论文字（`.verdict` 段落），只保留标题、下方的「依据 · 整体推理链」折叠与指标行。折叠区内容不变。

## 3. 接入真实数据后的前后端数据架构

这一节只做规划，不改代码；确认后再按此实现。

### 数据表（Lovable Cloud / Postgres）

```text
profiles            用户基本信息（与 auth.users 一一对应）
resumes             上传的简历文件记录（storage 路径、文件名、解析状态）
user_profiles       个人画像：8 维分数 + 经验/技能/动机/风险四段结构化 JSON
                    永久保存，只有用户主动「重新建立」才新增版本
job_profiles        岗位画像：JD 原文、公司/职位、8 维分数、结构化解析
match_reports       一次匹配分析结果：user_profile_id + job_profile_id
                    存总分、一句话决策、三个判断、投前 3 步、分项评分、推理链
compare_pool        对比池：用户 × 岗位，含加入时间
applications        投递记录：岗位、匹配分、正文/引用、当前状态
application_events  状态流转事件流：application_id + status + occurred_at
                    时间轴与统计全部由这张表推导，不再靠前端本地存储
```

要点：

- 画像用「版本」而非覆盖：`user_profiles` 保留历史，`is_current` 标记当前版本；重新建立画像=新增一版并把旧版置为非当前，用户删除才真正删除。
- 匹配报告是可复现的产物：同一对（画像版本，岗位画像）唯一，画像换版本时报告自动失效并可重算，保证 Match 页展示的永远是基于当前画像与该岗位 JD 的真实分析。
- 时间轴是事件流：状态每次变更写一条 `application_events`，前端按 `occurred_at` 倒序渲染，天然满足第 1 项需求，也能回看历史。
- 所有表 RLS 按 `auth.uid()` 限定本人可读写，并配套 GRANT。

### 服务端逻辑（Edge Functions）

- `parse-resume`：简历文件 → 结构化画像 + 8 维打分，写入 `user_profiles`。
- `parse-jd`：JD 文本 → 岗位画像，写入 `job_profiles`。
- `run-match`：取当前用户画像 + 岗位画像 → 生成一句话决策、三判断、投前 3 步、逐条依据与推理链，写入 `match_reports`。
- AI 调用全部在服务端，密钥不进前端。

### 前端改造路径

- 现有 5 个静态原型页迁移为 React 路由页，交互逻辑（折叠、状态下拉、对比池分环、跳转）原样保留。
- 现在的 `localStorage` 读写集中在少数函数里，届时把这一层整体换成数据接口调用，页面组件不用改。
- 未登录时仍可用本地存储作为演示态；登录后自动迁移到账号数据。
