# 招聘平台岗位抓取：技术架构（第一阶段：只抓取、看质量）

## 结论先行
推荐**用现有浏览器扩展，在用户自己已登录的浏览器里读取推荐岗位**，而不是让服务器拿用户账号去登录 BOSS直聘/脉脉。

| 方案 | 做法 | 问题 |
|---|---|---|
| A. 服务器代登录（GitHub 上常见的 Playwright / DrissionPage 脚本） | 用户把账号或 Cookie 交给我们，云端无头浏览器定时登录抓取 | 要保存用户登录凭证，风险极高；BOSS/脉脉有滑块验证、设备指纹和异地登录检测，容易触发风控甚至封号；云函数跑不了长时间浏览器 |
| **B. 扩展在用户本机抓取（推荐）** | 扩展打开用户已登录的推荐页，读取页面上的岗位列表，上传到我们后台 | 只有电脑开着浏览器时才能在定时点运行；平台页面改版时需要更新选择器 |

开源项目只借鉴它们的**页面字段解析思路**（岗位卡片、薪资、公司、详情页结构），不照搬它们的“代登录 + 自动投递”架构。

## 整体流程
```text
每天 10:00 / 22:00（扩展定时器；错过时下次打开浏览器补跑）
  -> 扩展在后台标签页打开：BOSS推荐页、脉脉职位推荐、猎聘/拉勾（逐步扩展）
  -> 读取推荐列表 + 前 N 个岗位详情（限速，模拟正常浏览，每平台每次 ≤30 条）
  -> 上传到后台「抓取收件箱」(按 平台+岗位ID 去重)
  -> 后台规则初筛（城市/薪资/岗位方向/经验）
  -> 通过者用已有岗位画像 + 匹配评分逻辑打分
  -> 每天选出 ≤10 个最匹配的岗位，进入「今日推荐」
```

## 第一阶段要做的（只验证抓取质量，暂不设计推荐交互）
1. **扩展新增“推荐岗位采集”**：BOSS直聘、脉脉两个平台先做；定时 + 手动「立即抓取」按钮；未登录时提示用户去登录，不做任何登录操作。
2. **后台新增抓取收件箱**：保存原始字段（标题、公司、薪资、城市、经验、学历、JD 全文、原链接、来源平台、抓取时间），每个用户只能看到自己的。
3. **字段完整度检查**：每条记录标注缺了哪些字段（如 JD 没抓全），用来评估准确性。
4. **一个简单的检查页**（仅自己看）：按平台列出抓取结果、完整度、重复率，方便你判断质量。
5. **不做**：自动投递、自动打招呼、服务器保存账号密码或 Cookie。

## 第二阶段（质量确认后）
- 规则初筛 + 匹配评分，每天 ≤10 个推送到产品内；推荐理由引用画像对比。
- 用户反馈（感兴趣/不合适）回流调整筛选条件。

## 风险与边界
- 自动化读取可能违反平台用户协议；我们控制频率、只读、不自动投递，以降低风控概率，但无法保证零风险，需在产品里告知用户。
- “早晚 10 点”依赖用户电脑开机、浏览器打开；手机端小程序无法做到。
- 平台改版会导致解析失效，需要完整度监控及时发现。

## 技术细节
- 扩展：`chrome.alarms` 定时；`chrome.tabs.create({active:false})` + content script 解析 DOM；每平台独立解析器模块；随机间隔 3–8 秒。
- 认证复用现有扩展的每用户可撤销令牌，新增 `ingest-jobs` 云函数批量写入。
- 新表 `scraped_jobs`（user_id、platform、platform_job_id 唯一、原始字段、completeness、raw_html_hash、fetched_at），开启 RLS 仅本人可读。
- 后续评分直接复用现有 parse-jd 与匹配评分；每日推荐上限 10 写成可测试规则。
