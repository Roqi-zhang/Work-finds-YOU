# 接入真实数据与 AI · 决策清单与架构评估

目标：把现在的静态原型变成一个任何人可访问、支持大量用户与数据、长期可迭代、跑在自有域名上的正式产品。下面先给需要你拍板的决策，再给现有架构的差距与改进建议。

---

## 一、需要你做决定的事项（含我的建议）

### D1. AI 模型选型
产品里有三类 AI 任务：简历解析、JD 解析、匹配分析（决策 + 三判断 + 投前 3 步 + 推理链）。

建议：全部走 Lovable AI Gateway，模型统一用 `openai/gpt-5.6-sol`。
- 匹配分析是产品的命门，需要长上下文、稳定的结构化输出、可解释的推理链，用最强模型最划算。
- 解析类任务（简历/JD → 结构化字段）也用同一个模型，保证抽取口径一致；先跑准确度，量大之后再考虑分流。
- 不需要你提供任何 API Key，密钥由平台注入，只在服务端使用。
- 输出全部用结构化 schema 约束（decision / judgements[3] / steps[3] / dimension_scores[8] / sources[] / reasoning_trace），保证前端插槽稳定。

需要你确认：是否接受统一用这个模型；是否需要文件（PDF/图片）直传给模型做多模态解析，还是先做文本提取再送模型。

### D2. 简历 / JD 的解析路径
- 方案 A（建议）：PDF 与图片直接交给多模态模型读，减少一层依赖，版式复杂的简历表现更好。
- 方案 B：先用解析库抽文本再送模型，便宜一些，但对扫描件、双栏排版容易丢信息。
Word 文档两种方案都需要先转文本。

### D3. 打分口径与可复现性
8 维分数是产品信任的基础。需要定：
- 分数由模型直接给，还是模型给证据、由固定规则算分（建议后者：模型只负责抽取与判断，分数用可解释的规则合成，避免同一份简历两次跑出不同分）。
- 匹配报告是否缓存：建议同一对（画像版本，岗位画像）只算一次并入库，画像更新时旧报告标记失效。

### D4. 账号与用户隔离
建议：邮箱密码 + Google 登录两种方式，全部数据按用户隔离。
需要你定：未登录游客是否可以试用一次（建议可以，试用数据存本地，登录后一次性迁移）。

### D5. 额度与付费
PRD 里提过「普通用户只能建 1 次画像」。需要定：
- 免费额度：建议 1 次画像 + 3 次匹配分析。
- 付费层级：建议两档（月付 / 年付），区分画像重建次数、对比池容量、匹配分析次数。
- 是否现在就接支付，还是先上线免费版、后加。建议先上线，把额度计数做好，支付后接。

### D6. 数据保留与导出
- 画像是否保留历史版本（建议保留，`is_current` 标记当前版）。
- 用户删除账号时的数据处理方式。
- 是否提供导出（投递记录导出 CSV 是低成本高感知的功能）。

### D7. 域名与环境
需要你准备一个域名。需要定：
- 是否需要独立的测试环境（建议：预览环境 + 正式域名两套，功能先在预览验证再发布）。
- 主域名用根域还是 www。

### D8. 版本更新策略
你要求支持推出不同版本的更新。需要定：
- 是否需要功能开关（让新功能先对部分用户开放）。
- 是否需要站内更新日志页。

## 二、现有架构能否支撑你的要求

现状：6 个独立静态 HTML 放在 `public/previews/`，React 侧只有一个 iframe 外壳；所有数据在浏览器 localStorage；没有账号、没有数据库、没有服务端。

| 你的要求 | 现状 | 结论 |
| --- | --- | --- |
| 任何人可访问 | 发布后可访问 | 满足 |
| 大量用户 | 无账号体系 | 不满足 |
| 大量数据存储 | 只在浏览器本地 | 不满足 |
| 自有域名 | 未接 | 可接，需你提供域名 |
| 长期维护 | 6 份 HTML 各自复制逻辑 | 不满足 |
| 多版本更新 | 无版本机制 | 不满足 |

结论：当前是可用的高保真原型，不是可长期运营的产品底座。要达成你的目标，必须补三层：后端（数据库 + 认证 + 存储 + 服务端 AI 调用）、前端工程化（HTML → React 路由页）、运营能力（额度、版本、监控）。

## 三、改进建议（实施顺序）

### 阶段 1 · 打地基
1. 开启 Lovable Cloud（数据库 / 认证 / 文件存储 / 服务端函数一次到位）。
2. 建表并配 RLS 与授权：`profiles`、`resumes`、`user_profiles`、`job_profiles`、`match_reports`、`compare_pool`、`applications`、`application_events`、`usage_counters`。
3. 接入登录（邮箱密码 + Google），未登录保留演示态。

### 阶段 2 · 前端迁移
4. 把 6 个 HTML 逐页迁成 React 路由页，视觉与交互 1:1 还原（花朵、月相、贝塞尔连线保留），`_shared.css` 的 Token 转成设计系统变量。
5. 现有 `_data.js` 数据层原地换成接口调用，页面组件不动。

### 阶段 3 · 接 AI
6. 三个服务端函数：`parse-resume`、`parse-jd`、`run-match`，全部结构化输出，密钥不进前端。
7. 增加失败态与重试（现在的分析是假异步，没有失败路径）。
8. 长任务改为任务记录 + 轮询，避免请求超时。

### 阶段 4 · 运营化
9. 额度计数与付费层级。
10. 自有域名接入。
11. 错误监控与 AI 调用日志（用于核算成本与排查错误结论）。

## 四、技术说明

- 后端用 Lovable Cloud（Postgres + Auth + Storage + Edge Functions），横向扩展与备份由平台负责，实例规格可随用户量上调。
- 所有表按 `auth.uid()` 做行级隔离，并显式授权，避免越权读取。
- AI 调用全部在服务端函数内完成，前端只拿结果。
- 时间轴与统计由 `application_events` 事件流推导，不再依赖前端本地状态。
- 版本更新：正式域名与预览环境分离，发布即更新；如需灰度，用数据库里的功能开关表控制。
