# 匹配一致性 · 缓存复用 · 动效与分数同步

## 1. 双花合并动效改为持续循环

现在的循环靠 JS 定时器把状态在「分开 / 合并」间来回切，切换瞬间会停顿、看起来像合并完就不动了。改为纯 CSS 无限动画：两朵花以 `alternate` 无限往返（分开 → 交叠 → 分开），请求返回时才淡出。定时器逻辑删除。

## 2. 已匹配过的组合不再重复分析

`进入匹配` 目前强制 `force = true`，每次都重跑模型。改为默认走缓存：

- 前端改为 `runMatch(jobId)`（不强制）。
- 后端已有「同一份画像 + 同一岗位有成功报告就直接返回」的短路逻辑，命中即秒开 Match 页。
- Match 页保留一个「重新分析」入口用于强制重算（现有逻辑不变）。

## 3. 同一份简历 + 同一份 JD 分数不一致

已查证数据库：同一岗位下存在两条报告，78 分与 91 分，对应两条**不同的个人画像记录**（一条是无目标岗位的通用画像，一条是针对该岗位生成的画像），两次分析的证据分层不同，模型给出的档位也不同，所以确定性公式算出不同分。

修复方式：

- **画像去重**：同一简历内容 + 同一目标岗位（含"无目标岗位"）已存在成功画像时，直接复用该画像记录，不再新建一条。
- **匹配去重**：匹配报告以（画像内容指纹 + 岗位内容指纹）为准查缓存，而不仅是行 id，这样同一简历重传后仍命中同一份报告。
- **降低模型抖动**：匹配与画像调用固定 `temperature: 0`（模型支持时），让同样输入尽量得到同样档位。
- 结果：同一简历 + 同一 JD 永远只有一个分数。

## 4. 同一份 JD 重复上传仍然慢

缓存本身是有的（同 hash 直接返回，不调模型），慢在命中之前的步骤：文件要先从存储下载、PDF/DOCX 抽文本、再算 hash。改为：

- 前端在上传前就本地算出文件字节的 hash，随请求一起带上；后端先用它查缓存，命中就直接返回，完全跳过下载与解析。
- 未命中时才走原有下载 → 抽取 → 解析流程（内容 hash 仍按现规则写入，保证跨用户复用不受影响）。

## 5. 投递管理的匹配分不会更新

投递记录在创建时把分数快照写进了本地存储，之后再也不更新。改为：

- 投递页加载时按岗位 id 批量读取最新匹配报告，用最新分数覆盖显示并回写本地记录。
- 摘要文案里的「匹配 XX%」同步刷新；平均分统计随之更新。

## 技术说明

- 动效：`src/styles/pages/profile.css` 增加 `mergeLoop` keyframes（`infinite alternate`），`src/pages/Profile.tsx` 移除 `setInterval` 循环。
- 缓存：`src/lib/ai.ts` 上传前用 SubtleCrypto 计算 sha256 并传 `clientHash`；`parse-jd` / `parse-resume` 在下载前先查。
- 画像/报告去重：`parse-resume` 复用同 `(content_hash, target_job_profile_id)` 的成功画像行；`run-match` 缓存查询以画像与岗位的内容指纹为条件。
- 分数同步：`src/lib/wfy.ts` 增加 `refreshApplicationScores()`，`Delivery.tsx` 挂载时调用。
- 不改任何页面布局与交互结构。
