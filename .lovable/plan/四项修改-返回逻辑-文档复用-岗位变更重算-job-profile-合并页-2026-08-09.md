# 四项修改：返回逻辑 / 文档复用 / 岗位变更重算 / JOB+PROFILE 合并页

## 1. 返回按钮按导航顺序回退

现在 JOB 页与 PROFILE 页的「← 返回」都调用 `history.back()`，所以会回到「上一次停留的页面」，而不是导航上的前一站。改为固定顺序回退：

```text
01 HOME → 02 JOB·PROFILE(合并页) → 03 MATCH → 04 COMPARE → 05 DELIVERY
```

- 合并页返回 → HOME
- MATCH 返回 → 合并页（带上当前岗位参数）
- COMPARE 返回 → MATCH，DELIVERY 返回 → COMPARE

不再使用浏览器历史，改为固定路由跳转。

## 2. 简历 / JD 的去重存储与复用（现状评估）

已经做到了，机制如下：

- 每份文档按内容算 SHA-256，写入文档库（`documents`），重复上传只累加计数，不重复入库。
- 每一层分析结果按「内容指纹 + 分析阶段 + 提示词版本」存进分析缓存（`document_analyses`），同一份文档再次上传直接取旧结果，不再调模型。
- JD 的分析结果是全站共享的（别人传过同一份 JD，你也能秒出结果）；简历的分析结果只在本人范围内复用，避免个人隐私跨账号泄漏。
- 上传前浏览器就先算好指纹随请求带上，命中缓存时连文件下载和 PDF/Word 抽取都跳过。

效果：重复文档的模型消耗降到 0，返回时间从十几秒降到一秒内。

本次要补的一个缺口：JD 缓存目前只在「同一用户/同一设备」范围内查，全局复用没有真正生效。改为先按内容指纹查全局分析缓存，命中后只为当前用户生成一条岗位记录，不再调模型。

## 3. 岗位画像更新后必须重新匹配

已查证代码：简历重新解析时会把相关匹配报告标记为「过期」，但 **JD 重新解析没有做这一步**。所以更新岗位画像后，`进入匹配` 命中旧报告缓存，看起来「没感知到岗位变更」。

修复：JD 解析写回岗位记录时，若内容指纹与上一次不同，就把该岗位下所有匹配报告标记为过期；匹配时忽略过期报告、重新分析一次，之后再进就走新缓存。

## 4. JOB 与 PROFILE 合并为一页

新地址 `/workbench`，`/jobprofile` 与 `/profile` 都重定向过去。导航改为：

```text
01 HOME   02 WORKBENCH   03 MATCH   04 COMPARE   05 DELIVERY
```

布局（左右各占一半，桌面端并排，窄屏上下堆叠）：

- 左半边：原 JOB 页标题「解析岗位的理想能力花」＋说明文字在上，下面是原有的上传区、岗位能力花与分析列表，格式完全不变；去掉底部的「下一步 →」按钮，保留「重新建立岗位画像」。
- 右半边：原 PROFILE 页标题「创建属于你的能力花」＋说明文字在上，下面是原有的上传区、个人能力花与分析列表，格式完全不变；去掉底部的「进入匹配 →」按钮，保留「重新建立画像」。
- 页面底部居中一个统一的「进入匹配 →」按钮：两边都完成后才可点，点击后仍旧播放双花合并动效再进 MATCH。

功能、动效、上传校验、后台任务续跑、登录回跳全部保持现有行为，只是换了容器与位置。

## 技术说明

- 新增 `src/pages/Workbench.tsx`，由现有 `JobProfile.tsx` 与 `Profile.tsx` 拆出的两个栏目组件组合而成，样式沿用 `jobprofile.css` / `profile.css`，新增一个两栏栅格与底部操作条的容器样式。
- `App.tsx` 增加 `/workbench` 路由，`/jobprofile`、`/profile` 改为 `<Navigate replace>`；`TopBar.tsx` 导航项与序号同步更新。
- 返回逻辑集中到一个 `prevRoute()` 映射，替换各页 `history.back()`。
- `parse-jd/index.ts`：全局分析缓存查询前置；更新岗位行时比对 `content_hash`，变更则 `match_reports.update({ stale: true })`。
- 双花合并动效与 `runMatch` 调用逻辑原样迁移到合并页底部按钮。
